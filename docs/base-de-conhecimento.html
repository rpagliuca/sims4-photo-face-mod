O CPython embutido no jogo

O The Sims 4 embute um interpretador CPython 3.7.0 desde a atualização de novembro de 2018 (a mesma atualização que trocou o sufixo dos módulos compilados de .pyo para .pyc, seguindo a mudança do próprio CPython 3.7 que unificou os dois). Não há indício de que essa versão tenha sido atualizada desde então — todo o ecossistema de mods da comunidade (S4CL, Wicked Whims, MC Command Center, etc.) ainda assume 3.7.0 como alvo.

Isso importa diretamente para o build: o bytecode .pyc empacotado no .ts4script precisa ter o magic number correspondente ao CPython 3.7. Compilar com um Python mais novo (3.10, 3.11...) produz bytecode incompatível que o jogo rejeita silenciosamente ou trava com "Last Exception". Ver detalhes de build em Compilação.

O formato .ts4script

Um arquivo .ts4script é, estruturalmente, um ZIP renomeado contendo módulos Python — tanto .py (código-fonte) quanto .pyc (bytecode pré-compilado) funcionam, mas a prática da comunidade é distribuir só .pyc para reduzir tamanho e (marginalmente) dificultar leitura casual do código. O jogo varre a pasta Mods/, identifica arquivos com essa extensão e os injeta no sys.path do interpretador embutido, como se fossem pacotes Python normais.

Regra de profundidade: o jogo só reconhece .ts4script até 1 nível de subpasta dentro de Mods/ (ex.: Mods/PhotoFaceMod/photofacemod.ts4script funciona; Mods/PhotoFaceMod/dist/photofacemod.ts4script não é carregado). Arquivos .package são mais tolerantes e funcionam até uns 5-6 níveis de profundidade. Essa assimetria é uma causa comum de "meu mod não aparece" — ver Troubleshooting em Instalação.

Padrões de script mod (S4CL)

A API da EA para scripting não é documentada oficialmente; o conhecimento vem de engenharia reversa e de frameworks comunitários. O mais usado é o Sims4CommunityLibrary (S4CL) — o repositório original desapareceu e a comunidade migrou para o fork DeviantGameMods/Sims4CommunityLibrary (licenciado CC BY 4.0). Ele expõe três padrões que este mod usa:

  • @sims4.commands.Command — decorator nativo do jogo (não é do S4CL) que registra uma função Python como comando de console, invocável via Ctrl+Shift+C no jogo (ex.: photoface.assign nome_do_sim caminho_da_foto). É o gancho mais simples e estável para interação do jogador com o mod, sem precisar de UI customizada.
  • CommonInjectionUtils.inject_safely_into (S4CL) — permite "envolver" (wrap) um método de uma classe do jogo sem herdar dela nem sobrescrever o arquivo original, chamando o comportamento original e adicionando lógica antes/depois. É como o mod se anexa a comportamentos existentes (ex.: aplicar o acessório sempre que um Sim é instanciado em uma zona) sem conflitar com outros mods que fazem o mesmo.
  • CommonEventRegistry.handle_events (S4CL) — sistema de eventos do S4CL sobre os hooks nativos do jogo. Eventos relevantes para este mod: ZoneEarlyLoadEvent e ZoneLateLoadEvent (disparados ao carregar um lote/save) e SaveEvent (dispara inclusive quando o jogador fecha o jogo sem salvar manualmente, o que o torna mais confiável que tentar interceptar só o menu "Salvar").

DBPF: o formato de .package

DBPF (Database Packed File) é o formato de contêiner usado por todos os jogos da Maxis/EA desde o SimCity 4 — SimCity 4, Os Sims 2/3/4 todos usam variações dele. Um .package é basicamente um índice de recursos, cada um endereçado por uma chave composta:

  • Type ID (32-bit) — que tipo de recurso é (textura, tuning, geometria...)
  • Group ID (32-bit) — agrupamento lógico, frequentemente 0x00000000
  • Instance ID (64-bit) — identificador único do recurso dentro do tipo/grupo

O header do arquivo tem 96 bytes fixos com metadados (versão do formato, contagem de entradas do índice, offset do índice). Os dados de cada recurso podem estar comprimidos com RefPack/QFS, um algoritmo de compressão LZ77-like proprietário da Maxis anterior ao zlib virar padrão de fato.

Isso não foi confirmado na prática; a suposição seguranca é que CASP exige textura no formato DST comprimido, e é isso que o pipeline atual assume. Se alguém validar o caminho IMAG no futuro, vale revisitar e simplificar a companion tool.

CASP: acessórios e o template base

Um acessório CAS (CAS Part) é a unidade que o jogo entende como "algo equipável" — chapéu, óculos, colar, etc. Ele é composto por várias entradas DBPF interligadas: o registro CASP (metadados: nome, slot de equipamento, faixa de idade/gênero, referências), a(s) textura(s), a geometria e o thumbnail.

Criar um CASP do zero via código é possível em teoria, mas envolve reproduzir uma quantidade grande de metadados e convenções que o Sims4Studio (ferramenta GUI da comunidade) já resolve de forma confiável. A decisão deste projeto foi: criar o CASP base uma única vez no Sims4Studio, já com N swatches (variações) — um acessório de cabeça simples, plano, do tamanho de uma foto, com (por exemplo) 8-16 swatches reservados — e versionar esse .package "template" no repositório (packages/casp_template/). Cada swatch já nasce com sua própria resource key de textura distinta, corretamente referenciada pelo CASP internamente (o Sims4Studio cuida disso na hora de criar os swatches). A companion tool então abre esse template com o S4TK e substitui apenas a textura do swatch correspondente ao índice atribuído a um Sim específico (ver persistência por Sim), sem tocar no CASP nem nos outros swatches. Como cada swatch tem uma resource key própria, pacotes gerados para Sims diferentes (índices diferentes) sobrescrevem chaves diferentes e coexistem sem conflito quando instalados juntos — ao contrário de uma abordagem ingênua de "uma textura só", que faria o último pacote instalado sobrescrever a foto de todo mundo. Isso evita reimplementar toda a complexidade de geração/parsing binário de CASP do zero.

Sims4Studio é GUI-only, sem CLI, e roda em .NET (Windows nativo ou Wine + .NET 6 Desktop Runtime no Linux). A criação do template é, por natureza, um passo manual/único feito pelo mantenedor — não faz parte do pipeline de build repetido a cada foto. O CI tenta automatizar a geração via Wine de forma best-effort (ver Compilação), mas isso é experimental; se a automação falhar ou ficar frágil, o caminho de fallback documentado é gerar/atualizar o template manualmente no Windows ou numa VM e commitar o resultado.

O rig e o osso b__Head__

Sims usam um esqueleto (rig) comum de humanoide, com convenção de nomenclatura de ossos prefixada b__ (bone). O osso da cabeça é b__Head__. Acessórios de cabeça (chapéus, óculos, brincos, e — neste mod — a "foto") são skinned rigidamente a esse osso: a geometria do acessório herda 100% da transformação (posição, rotação, escala) do osso, sem nenhum blend com ossos vizinhos. É o mesmo mecanismo que qualquer chapéu do jogo usa — não há nada de especial no acessório deste mod do ponto de vista do engine, só o conteúdo (a foto) e o propósito (cobrir o rosto) são diferentes do uso "normal".

Por que não existe billboard de verdade

"Billboarding" é a técnica clássica de sempre rotacionar uma geometria plana para encarar a câmera, independente da orientação do objeto/personagem ao qual está anexada — é como árvores e vegetação distante são renderizadas em praticamente todo jogo 3D, incluindo o The Sims 4. A pesquisa para este projeto não encontrou nenhum indício de que esse mecanismo esteja exposto para qualquer coisa anexada ao rig de um Sim: ele existe apenas no sistema de LOD de vegetação (árvores 2D vistas de longe), que é uma parte totalmente separada do pipeline de renderização de personagens.

Nenhum mod da comunidade documentado — em fóruns, wikis ou repositórios públicos consultados durante a pesquisa — relata ter conseguido billboard real em um acessório de Sim. A conclusão prática é que fazer o acessório "olhar sempre pra câmera" exigiria alterar o shader ou o pipeline de renderização do próprio engine, o que está completamente fora do alcance de CC (dados) ou de um script mod (lógica de jogo em Python rodando sobre a API exposta). É por isso que a arquitetura deste mod abraça o comportamento padrão de acessório rígido em vez de perseguir uma solução inviável — ver a explicação de design em Início.

Companion tool e S4TK

O jogo nunca lê um PNG solto em tempo de execução — só consome recursos já compilados dentro de um .package. Isso é uma limitação estrutural do engine, não uma escolha de design deste mod. O precedente mais próximo encontrado na comunidade é o Sims 4 Mod Manager, que também tem uma ferramenta companion separada (fora do jogo) para gerar uma tela de carregamento customizada a partir de uma foto do usuário — o mesmo padrão arquitetural adotado aqui: conversão offline, aplicação in-game.

Para a conversão PNG → formato de textura CAS (DST, um DDS "embaralhado" específico da Maxis) e a manipulação do contêiner DBPF, a busca por bibliotecas Python maduras (PyPI: pydbpf, python-dbpf e variações) não encontrou nada ativo ou confiável. O ferramental clássico da comunidade para DBPF, s4pi / Sims4Tools, é .NET Framework clássico e não foi portado para .NET Core/Mono — inviável de rodar de forma robusta em Linux.

A alternativa madura encontrada foi o Sims4Toolkit (S4TK), um conjunto de pacotes Node.js/TypeScript ativamente mantido, licenciado MIT:

  • @s4tk/models — leitura e escrita de .package (DBPF), incluindo compressão/descompressão RefPack.
  • @s4tk/images — conversão entre PNG e os formatos de textura DDS/DST usados pelo CAS, resolvendo a parte mais difícil do pipeline (o encoding DST "embaralhado").

Essa é a razão de a companion tool deste projeto ser Node.js e não Python: não é uma preferência de linguagem, é a ausência de alternativa Python madura para a parte que realmente importa (DBPF + DST). O script mod continua em Python porque essa parte é obrigatoriamente Python — é o que o jogo embute.

Persistência de dados por Sim

Não existe API nativa da EA para anexar um dado arbitrário (como "qual foto pertence a este Sim") a um objeto Sim de forma persistente através de save/load. Dois padrões de solução aparecem no S4CL:

Opção adotada: arquivo externo

CommonPersistedSimDataStorage / CommonFilePersistenceService do S4CL: um JSON externo, fora do save do jogo, em Mods/mod_data/<nome-do-mod>/, chaveado por sim_id combinado com o GUID do save slot (para não misturar dados entre saves diferentes ou saves duplicados/renomeados). É mais simples de implementar e depurar (é só um JSON legível), ao custo de viver fora do arquivo de save propriamente dito — copiar/mover só o .save sem levar a pasta mod_data junto perde a atribuição de fotos.

Alternativa mais robusta, não adotada inicialmente

CommonHiddenHouseholdPersistenceService do S4CL: grava um blob JSON no campo .description de um Household (residência) invisível criado só para esse fim, dentro do save de verdade do jogo. É mais robusto (viaja junto com o .save, sobrevive a backup/restore do save inteiro), mas mais complexo de implementar e de depurar. Fica documentado aqui como caminho de evolução caso o arquivo externo se mostre insuficiente na prática.
